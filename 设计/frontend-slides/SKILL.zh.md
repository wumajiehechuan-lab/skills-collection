# Frontend Slides

创建零依赖、动画丰富的 HTML 演示文稿，完全在浏览器中运行。

## 核心原则

1. **零依赖** — 单个 HTML 文件，包含内联 CSS/JS。无需 npm，无需构建工具。
2. **展示，而非描述** — 生成视觉预览，而非抽象选择。人们通过看到来发现他们想要什么。
3. **独特设计** — 没有通用的"AI 流水"。每个演示文稿都必须感觉是定制的。
4. **渐进式披露** — 首先读取轻量级的风格索引。对于大胆模板，使用小型预览卡片进行风格预览，仅在用户选择该模板后才加载完整的 `design.md`。
5. **固定的 16:9 舞台（不可协商）** — 每个演示文稿使用 1920×1080 的幻灯片画布，整体缩放以适应视口。幻灯片在每个屏幕上必须保持 16:9，包括手机。不要为适应设备而重新排版幻灯片内容。

## 设计美学

你倾向于收敛到通用的、"分布上"的输出。在前端设计中，这会创建用户所谓的"AI 流水"美学。避免这种情况：制作有创意的、独特的前端，令人惊喜和愉悦。

专注于：

- **排版**：选择美丽、独特、有趣的字体。避免像 Arial 和 Inter 这样的通用字体；而是选择提升前端美学的独特选择。
- **颜色与主题**：致力于有凝聚力的美学。使用 CSS 变量保持一致性。主色调加锐利点缀胜过胆怯的、均匀分布的调色板。从 IDE 主题和文化美学中汲取灵感。
- **动效**：使用动画制作特效和微交互。对于 HTML 优先考虑纯 CSS 解决方案。在可用时为 React 使用 Motion 库。专注于高影响时刻：一个精心编排的页面加载，带有交错的显示（animation-delay），会比分散的微交互创造更多愉悦。
- **背景**：创造氛围和深度，而非默认为纯色。分层 CSS 渐变，使用几何图案，或添加与整体美学匹配的上下文效果。

避免通用的 AI 生成美学：

- 过度使用的字体系列（Inter、Roboto、Arial、系统字体）
- 陈词滥调的配色方案（特别是白色背景上的紫色渐变）
- 可预测的布局和组件模式
- 缺乏上下文特定特征的千篇一律的设计

创造性地解释并做出意外选择，感觉真正为上下文设计。在浅色和深色主题、不同字体、不同美学之间变化。你仍然倾向于在多次生成中收敛到常见选择（例如 Space Grotesk）。避免这种情况：跳出框框思考是至关重要的！

## 固定舞台规则

这些不变量适用于每个演示文稿中的每张幻灯片：

- 每个演示文稿都有一个填满浏览器窗口的视口包装器。
- 每张幻灯片都在固定的 1920×1080 舞台内创作。
- 舞台均匀缩放以适应视口。可能会出现黑边/柱边；不得重新布局内容。
- 不要使用响应式断点为手机重新排列幻灯片内容。
- 在 1920×1080 设计尺寸下使用固定的内部幻灯片测量值。
- 幻灯片可见性必须由 `.active` / `.visible` 使用 `viewport-base.css` 中的 `visibility`、`opacity` 和 `pointer-events` 控制。不要使用 `display: none` / `display: block` 进行幻灯片切换；后面的布局类如 `.slide-content { display: flex; }` 可能会覆盖它们，使所有幻灯片同时可见。
- 仅在舞台外的非幻灯片 UI，或在完整舞台不切实际的小型回退预览中使用 `clamp()`。
- 包含 `prefers-reduced-motion` 支持
- 永远不要直接否定 CSS 函数（`-clamp()`、`-min()`、`-max()` 会被静默忽略）— 改用 `calc(-1 * clamp(...))`

**生成时，读取 `viewport-base.css` 并在每个演示文稿中包含其全部内容。**

### 内容密度模式

询问用户这主要是阅读型还是演讲型演示文稿，然后围绕该答案设计：

| 密度模式 | 最适合 | 设计行为 |
| ------------- | -------- | --------------- |
| **低密度/演讲主导** | 公开演讲、主题演讲式分享、现场讲解 | 每张幻灯片一个想法，大字体，强视觉层次，充足留白，最多 1-3 个项目符号，必要时更多幻灯片 |
| **高密度/阅读优先** | 报告、讲义、异步审核、详细内部文档 | 更多自包含幻灯片、结构化网格/表格/注释、4-8 个项目符号或 4-6 个卡片（当可读时）、更紧凑但仍有意的间距 |

基线限制仍然适用：无滚动、无溢出、无重叠面板、无低于舒适阅读大小的文本。如果内容超过选定的密度模式，将其拆分为更多幻灯片，而不是缩小到局促。

## 阶段 0：检测模式

确定用户想要什么：

- **模式 A：新演示文稿** — 从零开始创建。进入阶段 1。
- **模式 B：PPT 转换** — 转换 .pptx 文件。进入阶段 4。
- **模式 C：增强** — 改进现有 HTML 演示文稿。读取它，理解它，增强它。**遵循下面的模式 C 修改规则。**

### 模式 C：修改规则

在增强现有演示文稿时，固定舞台适配是最大风险：

1. **添加内容前：** 统计现有元素，对照密度限制检查
2. **添加图像：** 将其适配在 1920×1080 幻灯片画布内。如果幻灯片已经有最大内容，拆分为两张幻灯片
3. **添加文本：** 每张幻灯片最多 4-6 个项目符号。超过限制？拆分为续页幻灯片
4. **任何修改后，验证：** 幻灯片舞台保持 16:9，无文本溢出其卡片，无面板重叠，并且截图在 1280×720 和一个手机视口中看起来正确
5. **主动重组：** 如果修改会导致溢出，自动拆分内容并通知用户。不要等待被询问

**向现有幻灯片添加图像时：** 首先将图像移到新幻灯片或减少其他内容。绝不要在未检查现有内容是否已填满 1920×1080 幻灯片舞台的情况下添加图像。

## 阶段 1：内容发现（新演示文稿）

**一起问所有问题**，这样用户一次填完所有内容。如果当前环境提供原生结构化问题 UI，请使用它；否则在一条简洁的消息中询问，并带有清晰编号的选择：

**问题 1 — 目的**（标题："目的"）：
这个演示文稿是做什么的？选项：融资演示 / 教学教程 / 会议演讲 / 内部演示

**问题 2 — 长度**（标题："长度"）：
大约有多少张幻灯片？选项：短 5-10 / 中 10-20 / 长 20+

**问题 3 — 内容**（标题："内容"）：
内容准备好了吗？选项：所有内容已准备好 / 粗略笔记 / 仅主题

**问题 4 — 密度**（标题："密度"）：
演示文稿应该感觉多密集？选项：

- "低密度/演讲主导" — 大想法，更少文字，更多视觉呼吸空间
- "高密度/阅读优先" — 更多自包含细节用于异步阅读

**阶段 1 期间不要询问内联编辑。** 用户不应在看到草稿前选择编辑行为。内联编辑是草稿后提供的便利：默认包含，除非用户明确要求锁定/仅导出文件。

记住用户的密度选择。它影响幻灯片数量、排版比例、每张幻灯片的文本量、布局密度，以及是否偏好电影式演讲幻灯片或自包含阅读幻灯片。

如果用户有内容，请他们分享。

### 步骤 1.2：图像评估（如果提供了图像）

如果用户选择了"无图像" → 跳转到阶段 2。

如果用户提供了图像文件夹：

1. **扫描** — 列出所有图像文件（.png、.jpg、.svg、.webp 等）
2. **检查每张图像** — 使用代理可用的图像理解能力。如果无法读取图像，使用文件名/元数据，并仅在需要时询问用户澄清
3. **评估** — 对于每张图像：显示什么，可用或不可用（附原因），代表什么概念，主色调
4. **共同设计大纲** — 精选图像与文本一起为幻灯片结构提供信息。这不是"规划幻灯片然后添加图像" — 从一开始就围绕两者设计（例如，3 张截图 → 3 张功能幻灯片，1 个徽标 → 标题/结束幻灯片）
5. **确认大纲**，在可用时使用相同的结构化问题机制："这个幻灯片大纲和图像选择看起来对吗？"选项：看起来不错 / 调整图像 / 调整大纲

**预览中的徽标：** 如果识别出可用的徽标，请在阶段 2 的每个风格预览中嵌入它（base64）— 用户会看到他们的品牌以三种不同风格呈现。

## 阶段 2：风格发现

**这是"展示，而非描述"阶段。** 大多数人无法用语言表达设计偏好。

### 步骤 2.0：直接生成 3 个风格预览

根据目的、受众、氛围和内容密度，生成 3 个不同的单幻灯片 HTML 预览，展示排版、颜色、动画和整体美学。

不要询问用户是否想要选项或预设选择器。默认发现体验始终是视觉比较。

如果用户已经给出了氛围，请使用它。如果他们没有，从场合、受众、内容和重要性推断可能的氛围。保持选项足够多样化，以便用户可以视觉反应，而无需预先表达品味。

如果用户明确命名预设或大胆模板，请将其作为一个选项，并围绕它生成其余预览槽位。

读取 [STYLE_PRESETS.md](STYLE_PRESETS.md) 以获取安全预设候选者。如果存在 [bold-template-pack/selection-index.json](bold-template-pack/selection-index.json)，也读取该紧凑索引，但不要读取任何 `design.md` 文件。

| 氛围 | 建议预设 |
| ------------------- | -------------------------------------------------- |
| 印象深刻/自信 | Bold Signal, Electric Studio, Dark Botanical |
| 兴奋/精力充沛 | Creative Voltage, Neon Cyber, Split Pastel |
| 冷静/专注 | Notebook Tabs, Paper & Ink, Swiss Modern |
| 启发/感动 | Dark Botanical, Vintage Editorial, Pastel Geometry |

**预览混合规则：**

- 默认生成 3 个预览：1 个来自 `STYLE_PRESETS.md` 的安全预设，至少 1 个来自 `bold-template-pack/selection-index.json` 的大胆模板，以及 1 个通配符。
- 通配符可以是第二个大胆模板或自生成的自定义设计。选择为用户的场合、受众、氛围和内容创建最强烈、最有用对比的选项。
- 不要强制每个表达选项都来自模板库。如果简报有比可用模板更锐利、更具体的设计机会，使用通配符槽位自由设计。
- 对于保守或高风险演示，使安全预设特别克制；选择冷静、更高正式程度的大胆模板；使通配符是另一个克制模板或感觉权威而非装饰性的自定义设计。
- 对于表达性演示，保持安全预设作为可读的回退；选择一个强大的大胆模板；使通配符是冒险的、上下文特定的，并且与其他两个预览明显不同。
- 如果大胆模板匹配感觉很弱，使用通配符作为自定义设计或回退到另一个安全预设，而不是强制模板。

**自定义通配符设计规则：**

- 遵循上面的设计美学部分：无通用的"AI 流水"、无默认字体/颜色/布局选择、无紫色渐变在白色上的陈词滥调、无千篇一律的仪表板/卡片外观。
- 匹配用户说明的场合、受众、氛围/感觉和内容密度。自定义设计应该感觉是为这个演示文稿创作的，而不仅仅是"时尚的"。
- 做出有意的视觉主张：独特的排版、承诺的调色板、可识别的布局系统，以及一个强大的氛围或图形装置。
- 保持对完整演示文稿可行。预览必须暗示可以扩展为章节、内容、引用、比较和结束幻灯片的设计系统。
- 使用固定的 1920×1080 舞台规则，并通过与其他每个选项相同的预览真实性检查。
- 永远不要在幻灯片本身渲染"custom"、"wildcard"、"AI-generated"或设计过程标签。

**大胆模板选择规则：**

- 将用户目的和氛围与 `mood`、`tone`、`best_for`、`avoid_for`、`formality`、`density` 和 `scheme` 匹配。
- 将 `best_for` 示例视为软信号，而非严格的行业过滤器。
- 保持三个预览彼此真正不同。
- 选择大胆模板候选者后，仅从选择索引中的 `preview_md` 路径读取那些候选者的 `preview.md` 文件。
- 仅将 `preview.md` 用于标题幻灯片预览。不要读取完整的 `design.md` 文件，直到用户选择最终模板。
- 除非选定的最终 `design.md` 缺少关键的实现细节，否则不要读取或复制 `template.html`。

**预览真实性规则（不可协商）：**

- 每个风格预览必须看起来像用户演示文稿的真实第一张幻灯片，而不是诊断卡片。
- 永远不要在幻灯片上渲染内部工作流文本：无 `preview`、`generated from`、`preview.md`、`template`、`preset`、`style option`、`Option A/B/C`、文件名、路径或源文档标签。
- 永远不要在幻灯片本身渲染模板名称或 slug 名称。模板/风格名称仅属于给用户的消息中。
- 永远不要将用户要求说明渲染为幻灯片内容，例如"sharp and provocative"、"safe option"、"bold option"、"for internal sharing"或"audience: ..."，除非用户明确希望那个精确短语出现在演示文稿中。
- 如果幻灯片需要装饰元素，仅使用真实演示装饰元素：演示标题、章节标题、日期、作者、公司、页码，或来自用户材料的真实内容短语。
- 打开预览前，检查可见文本，如果出现任何内部元数据，请修改。

将预览保存到 `.frontend-slides/slide-previews/`（style-a.html、style-b.html、style-c.html）。每个都应该是自包含且紧凑的，显示一张动画标题幻灯片。

自动为用户打开每个预览。

### 步骤 2.1：用户选择

询问（标题："风格"）：
你喜欢哪个风格预览？选项：风格 A：[名称] / 风格 B：[名称] / 风格 C：[名称] / 混合元素

如果"混合元素"，询问具体细节。

## 阶段 3：生成演示文稿

使用阶段 1 的内容（文本，或文本+精选图像）和阶段 2 的风格生成完整演示文稿。

如果提供了图像，幻灯片大纲已经从步骤 1.2 整合了它们。如果没有，CSS 生成的视觉效果（渐变、形状、图案）提供视觉趣味 — 这是一个完全支持的一流路径。

在整个演示文稿中应用用户的密度选择：

- **低密度/演讲主导：** 使用更多幻灯片，每张幻灯片更少想法。偏好大标题、短短语、视觉隐喻、章节节奏、引用/声明幻灯片，以及对演讲者友好的节奏。
- **高密度/阅读优先：** 使幻灯片更自包含。使用结构化网格、比较表格、注释图、标题，以及简洁的解释性文字。保持层次结构强大，使其感觉设计过，而不是像粘贴到幻灯片上的文档。

如果用户的说明需求混合，选择两种模式中更接近的一种，而不是发明中间选项：现场受众说服默认低密度；异步分发或详细审核默认高密度。

永远不要让高密度变成视觉混乱。如果高密度幻灯片开始溢出，拆分它或重新设计为更清晰的结构。

如果用户从 `bold-template-pack` 选择了大胆模板，在生成前读取那个模板的完整 `design.md`。不要读取其他大胆模板。将 `design.md` 视为设计食谱：

- 保存其字体、调色板、装饰词汇、间距节奏和组件语法。
- 将最终演示文稿生成为固定的 1920×1080 舞台，均匀缩放以适应视口，无论源模板最初是否使用 `deck-stage.js` 或视口流动 CSS。
- 将 `design.md` 中的视口流动值视为要转换为 1920×1080 舞台坐标的设计比例。不要在最终演示文稿中保留它们作为实时视口重排规则。
- 保持输出为单个自包含的 Frontend Slides HTML 文件。
- 不要复制演示幻灯片内容或过于字面地模仿源模板。
- 仅将 `template.html` 用作选定模板的最后手段实现参考。
- 生成后，在渲染的浏览器截图中验证内容溢出和面板重叠。仅 `scrollHeight` 检查是不够的，因为网格面板可以视觉上相互覆盖。

如果用户选择了自生成的自定义通配符，将该预览的 CSS 和布局视为设计食谱：

- 保存其字体、调色板、装饰词汇、间距节奏、网格逻辑和组件语法。
- 将相同的视觉系统扩展到完整演示文稿。用户选择自定义方向后，不要切换到预设或大胆模板。
- 从该系统设计任何缺失的幻灯片布局，而不是从另一种风格导入模式。
- 保持输出固定舞台、单个文件，并且像其他每个演示文稿一样视觉验证。

**生成前，读取这些支持文件：**

- [html-template.md](html-template.md) — HTML 架构和 JS 功能
- [viewport-base.css](viewport-base.css) — 强制 CSS（完整包含）
- [animation-patterns.md](animation-patterns.md) — 所选感觉的动画参考

**关键要求：**

- 单个自包含的 HTML 文件，所有 CSS/JS 内联
- 在 `<style>` 块中包含 viewport-base.css 的全部内容
- 使用 Fontshare 或 Google Fonts 的字体 — 永远不要系统字体
- 添加解释每个部分的详细注释
- 每个部分需要清晰的 `/* === 部分名称 === */` 注释块

## 阶段 4：PPT 转换

转换 PowerPoint 文件时：

1. **提取内容** — 运行 `python scripts/extract-pptx.py <input.pptx> <output_dir>`（必要时安装 python-pptx：`pip install python-pptx`）
2. **与用户确认** — 展示提取的幻灯片标题、内容摘要和图像数量
3. **风格选择** — 进入阶段 2 进行风格发现
4. **生成 HTML** — 转换为所选风格，保留所有文本、图像（来自 assets/）、幻灯片顺序和演讲者备注（作为 HTML 注释）

## 阶段 5：交付

1. **清理** — 删除 `.frontend-slides/slide-previews/` 如果存在
2. **打开** — 使用 `open [filename].html` 在浏览器中启动
3. **总结** — 告诉用户：
   - 文件位置、风格名称、幻灯片数量
   - 导航：箭头键、空格、如果启用则滑动/点击
   - 如何自定义：`:root` CSS 变量用于颜色，字体链接用于排版，`.reveal` 类用于动画
   - 内联文本编辑可用：悬停左上角或按 E 进入编辑模式，点击任何文本编辑，Ctrl+S 保存
   - 提供自然的草稿后动作：请求修订、直接在浏览器中编辑文本，或导出/分享

## 阶段 6：分享与导出（可选）

交付后，**询问用户：** _"你想分享这个演示文稿吗？我可以将其部署到实时 URL（在包括手机在内的任何设备上都有效）或将其导出为 PDF。"_

选项：

- **部署到 URL** — 在任何设备上都有效的可分享链接
- **导出为 PDF** — 用于电子邮件、Slack、打印的通用文件
- **两者都要**
- **不用了，谢谢**

如果用户拒绝，在此停止。如果他们选择一个或两个，继续下面。

### 6A：部署到实时 URL（Vercel）

这将演示文稿部署到 Vercel — 一个免费的托管平台。链接在任何设备上都有效（手机、平板电脑、笔记本电脑），并保持在线直到用户将其删除。

**如果用户从未部署过，逐步引导他们：**

1. **检查 Vercel CLI 是否已安装** — 运行 `npx vercel --version`。如果未找到，先安装 Node.js（macOS 上 `brew install node`，或从 https://nodejs.org 下载）。

2. **检查用户是否已登录** — 运行 `npx vercel whoami`。

3. **如果未登录，引导他们** — 运行 `npx vercel login` 并遵循提示（推荐使用 GitHub 登录）。

4. **部署演示文稿** — 运行 `bash scripts/deploy.sh [presentation.html]` 或 `bash scripts/deploy.sh [deck-folder/]`。

5. **交付链接** — 脚本输出部署 URL。告诉用户：
   - URL 是什么
   - 它在任何设备上都有效，包括手机
   - 他们可以通过再次运行部署来更新它
   - 他们可以在 https://vercel.com/dashboard 管理部署

### 6B：导出为 PDF

这使用 Playwright 将每个幻灯片捕获为 1920×1080 截图，并将它们组合成一个 PDF。

1. **运行导出脚本** — `bash scripts/export-pdf.sh [path-to-html] [output.pdf]`

2. **向用户解释幕后发生了什么：**
   - 无头浏览器以 1920×1080 打开演示文稿（标准宽屏）
   - 它逐个截图每个幻灯片
   - 所有截图组合成一个 PDF
   - 脚本需要 Playwright（浏览器自动化工具）— 如果缺失，它会自动安装

3. **如果 Playwright 安装失败：**
   - 最常见的问题是 Chromium 未下载。运行：`npx playwright install chromium`
   - 如果这也失败，可能是网络/防火墙问题。请用户在不同网络上尝试。

4. **交付 PDF** — 脚本自动打开它。告诉用户：
   - 文件位置和大小
   - 它在任何地方都有效 — 电子邮件、Slack、Notion、Google Docs、打印
   - 动画被其最终视觉状态替换（看起来仍然很棒，只是静态的）

**⚠️ PDF 导出注意事项：**

- **第一次运行很慢。** 脚本安装 Playwright 并将 Chromium 浏览器（约 150MB）下载到临时目录。每次运行都发生。警告用户第一次可能需要 30-60 秒 — 同一会话中的后续导出更快。
- **幻灯片必须使用 `class="slide"`。** 导出脚本通过查询 `.slide` 元素找到幻灯片。如果演示文稿使用不同的类名，脚本会报告"找到 0 张幻灯片"并失败。此技能生成的所有演示文稿都使用 `.slide`，因此这仅对外部创建的 HTML 很重要。
- **本地图像必须可通过 HTTP 加载。** 脚本启动本地服务器并通过它加载 HTML（以便 Google Fonts 和相对图像路径工作）。如果图像使用绝对文件系统路径（例如 `src="/Users/name/photo.png"`）而非相对路径（例如 `src="photo.png"`），它们不会加载。生成的演示文稿始终使用相对路径，但转换或用户提供的演示文稿可能不会 — 检查并修复如果需要。
- **只要图像在 HTML 文件的同一目录中（或相对目录），本地图像就会出现在 PDF 中。** 导出脚本通过 HTTP 提供 HTML 的父目录，因此像 `src="photo.png"` 这样的相对路径正确解析 — 包括带有空格的文件名。如果图像仍然不出现，检查：(1) 图像文件实际存在于引用路径中，(2) 路径是相对的，不是像 `/Users/name/photo.png` 这样的绝对文件系统路径。
- **大型演示文稿产生大型 PDF。** 每个幻灯片都捕获为完整的 1920×1080 PNG 截图。18 张幻灯片的演示文稿可以产生约 20MB 的 PDF。如果 PDF 超过 10MB，询问用户：_"PDF 是 [大小]。你想让我压缩它吗？它看起来会稍微不那么清晰，但文件会小得多。"_ 如果是，使用 `--compact` 标志重新运行导出：
  ```bash
  bash scripts/export-pdf.sh [path-to-html] [output.pdf] --compact
  ```
  这以 1280×720 而非 1920×1080 渲染，通常将文件大小减少 50-70%，视觉差异最小。
