# 演示文稿

`Presentations` 适用于严肃、高水准的演示文稿工作，"干净"远远不够。目标是创建一个可编辑的 PowerPoint 演示文稿，让人感觉像是由一位出色的编辑、一位优秀的分析师和一位杰出的设计师共同打造的。

此技能适用于分析叙事、投资者/运营回顾、战略故事、产品/业务绩效演示文稿，以及任何用户要求超越参考演示文稿的 PPTX 任务。

## 操作约定

仅使用 artifact-tool presentation JSX。捆绑的 Codex 运行时提供 `@oai/artifact-tool` 版本 2.7.3 或更高版本，并公开 `@oai/artifact-tool/presentation-jsx`。

不需要或导入单独的演示文稿运行时包。PPTX 导出/渲染行为必须通过 artifact-tool 访问。
对于模板跟随的精确克隆/编辑模式，生产 PPTX 边界是 artifact-tool 导入复制的初始 PPTX 和 `PresentationFile.exportPptx(presentation)`。不使用 Python、直接 OOXML 包编辑、LibreOffice 另存为或新幻灯片重建来修改最终的模板跟随演示文稿。

对于生成的光栅图像或参考稿，使用 Codex imagegen 工具。捆绑的脚本可以编写 imagegen 提示文件，但不得调用外部图像 API 或读取 API 密钥。

线程作用域路径：

- `SKILL_DIR=<已安装的 Presentations 技能的绝对路径>`
- `THREAD_ID=${CODEX_THREAD_ID:-manual-<timestamp-or-short-random-suffix>}`
- `WORKSPACE=$PWD/outputs/$THREAD_ID/presentations/<task-slug>`
- `SLIDES_DIR=$WORKSPACE/slides`
- `PREVIEW_DIR=$WORKSPACE/preview`
- `LAYOUT_DIR=$WORKSPACE/layout`
- `ASSET_DIR=$WORKSPACE/assets`
- `QA_DIR=$WORKSPACE/qa`
- `OUTPUT_DIR=<用户提供的输出目录，如果有的话，否则为 $WORKSPACE/output>`
- `FINAL_PPTX=$OUTPUT_DIR/<relevant-deck-title-slug>.pptx`

在命令和交接中使用绝对路径。将所有生成的规划文本笔记、预览 PNG、联系表、布局 JSON、imagegen 提示文件、临时参考图像和其他临时文件保存在此线程作用域的 `$WORKSPACE` 内。只将最终交付物保存在 `$OUTPUT_DIR` 中。如果用户提供外部输出目录，只将最终交付物写入或复制到那里；生成的 `.txt` 计划、联系表、预览、布局文件、提示文件和生成的脚本仍必须保留在 `$WORKSPACE` 下。
根据演示文稿主题或要求的交付物，为最终 PPTX 命名一个简短、相关的标题。不要使用通用文件名，如 `output.pptx`、`deck.pptx` 或 `deck.final.pptx`。

切勿使用操作系统临时文件夹、共享临时文件夹（如 `.presentation_workspaces`、`presentation-workspaces`、`presentation_workspaces`、`out`）或裸仓库本地演示文稿别名，除非路径位于 `outputs/$THREAD_ID/presentations/` 下。如果 `CODEX_THREAD_ID` 不可用，生成一个带有时间戳和短随机后缀的手动 ID。

## 北极星目标

演示文稿必须通过联系表测试。在缩略图大小下，它应该显示一个连贯的视觉系统、独特的幻灯片节奏和以证据为导向的叙事。在可读大小下，每张幻灯片应该有一个主张、一个证明对象，没有填充内容。

此技能拒绝"可用"的输出。演示文稿可能通过布局检查但仍然失败。如果更换公司名称后看起来像通用的 SaaS 仪表板、咨询卡片网格或自动生成的模板，请继续迭代。

## 强制工作流程

1. 确认任务模式。
2. 提取源故事。
3. 撰写主张框架。
4. 锁定设计系统。
5. 规划联系表。
6. 构建可编辑的 artifact-tool 幻灯片。对于模板跟随模式，导入并编辑复制的初始 PPTX，而不是从空白 JSX 重建映射的幻灯片；初始脚本在复制前验证 `template-frame-map.json`。
7. 渲染预览和布局 JSON。
8. 对于非模板模式，根据改进评分标准评分。
9. 对于非模板模式，迭代最弱的幻灯片。对于 `template-following`，使用 `$SKILL_DIR/profiles/template-and-edit.md` 中的模板跟随 QA 循环。
10. 仅在渲染的演示文稿满足其特定任务的 QA 门槛后，导出最终 PPTX。对于 `template-following`，门槛是源幻灯片保真度，而不是超越参考，并且包括 `$SKILL_DIR/profiles/template-and-edit.md` 中的模板保真度保护。
11. 在最终响应之前，清理生成的规划文本笔记、QA 临时文件、联系表、预览图像、生成的幻灯片模块/脚本、布局 JSON、清单、提示文本文件和其他临时图像。

### 任务模式

- `template-following`（模板跟随）：用户提供了源/模板演示文稿，其幻灯片骨架和视觉系统必须通过精确克隆/编辑继承。任何作为模板明确或隐式呈现的附加 PPTX 都路由到此处
- `create`（创建）：未提供演示文稿/模板；根据提示和源构建。
- `targeted-edit`（目标编辑）：对现有演示文稿进行小改动。

对于 `template-following`，保留源演示文稿的排版、调色板、间距、布局和品牌装饰，除非用户明确要求重新设计。对于 `targeted-edit`，保留现有演示文稿的视觉系统；可读性指导仅作为新添加或编辑内容的 QA 检查。

当源演示文稿和更好的参考演示文稿同时存在时，将它们分开：

- 源演示文稿：内容、必需部分、事实、现有材料。
- 参考演示文稿：质量标准、节奏、品味，以及证明可以产生更强输出的证据。

类似模板的表述包括 `template`、`follow this`、`use this style`、`same layout`、`corporate template`、`source deck`，或表示可重用模板的文件名/上下文。不要将类似模板的 PPTX 视为松散的质量参考。

对于非模板质量参考，不要盲目克隆参考。通过改进故事精度、构图变化、图表清晰度、留白和最终渲染质量来超越它。

### 演示文稿配置文件路由

在任务模式之后，精确选择一个主要的 `deck-profile`。这是一个硬性路由步骤，而不是标签练习。配置文件决定哪些证明对象、源规则、视觉密度、资产规则和 QA 门槛是阻塞性的。

配置文件：

- `finance-ir`（财务-投资者关系）：收益、投资者关系、运营回顾、财务分析。需要精确的报告数据、单位规范、来源脚注、过渡、表格和披露逻辑。
- `product-platform`（产品-平台）：SaaS/平台/产品叙事。需要架构图、工作流图表、采用证明、产品与财务的关联，且不使用通用功能卡片网格。
- `gtm-growth`（上市-增长）：上市、营销、消费者增长、订阅生态系统、移动性、客户参与。需要可见的增长循环、细分或群组证明、货币化过渡和品牌感知节奏。
- `engineering-platform`（工程-平台）：开发者、AI、基础设施、数据、安全和技术平台演示文稿。需要准确的系统图表、在高管简化后仍保留技术含义的标签，以及与架构相关的指标。
- `strategy-leadership`（战略-领导力）：投资者日、董事会、转型和市场战略演示文稿。需要章节规范、市场框架、战略赌注，以及承载论点的过渡幻灯片。
- `consumer-retail`（消费者-零售）：展示册、客户推销、奢侈品、消费者品牌、活动、旅行、生活方式、食品、时尚、美容、人物、地点、动物、体育、娱乐/儿童视觉叙事，以及其他需要观众视觉检查主题的以图像为主的演示文稿。需要真实资产或明确的资产来源、图像质量、编辑层次结构和客户就绪的文案。
- `template-following`（模板跟随）：用户提供了模板/源 PPTX，其幻灯片必须作为规范的可编辑起点。这仅适用于精确克隆/编辑：检查源幻灯片清单，将每个输出幻灯片映射到源幻灯片，复制映射的幻灯片，就地编辑复制的元素，并通过 artifact-tool 导出。需要 `template-audit.txt`、`template-frame-map.json` 和 `deviation-log.txt`；遵循 `template-and-edit.md`。
- `targeted-edit-data`（目标编辑-数据）：添加或编辑数据/比较幻灯片。需要在视觉工作之前进行精确计算，并将其原生地插入现有演示文稿。
- `targeted-edit-media`（目标编辑-媒体）：添加头像、徽标、截图或其他媒体。需要身份/来源验证、一致的裁剪，并保留源演示文稿的布局语法。
- `appendix-heavy`（附录密集）：密集的附录、表格、披露或来源包。需要索引/页码标记、可读的小字体阈值、表格语法和明确的来源密度规则。

如果任务模式是 `template-following`，执行路径始终是 `template-and-edit.md`；在主张框架中添加特定领域的配置文件门槛（如 `finance-ir` 或 `consumer-retail`）作为次要约束。对于非模板任务，如果多个配置文件适用，选择产生最高交付风险的配置文件作为主要配置文件，然后在主张框架中列出次要门槛。

选择配置文件后，如果任务重大或不熟悉，请阅读 `$SKILL_DIR/profiles/` 下的相应文件：

- `finance-ir.md`
- `product-platform.md`
- `gtm-growth.md`
- `engineering-platform.md`
- `consumer-retail.md`
- `template-and-edit.md`
- `appendix-heavy.md`

创建 `$WORKSPACE/profile-plan.txt`，包含：

- 任务模式
- 主要演示文稿配置文件
- 次要配置文件门槛（如有）
- 必需的证明对象
- 来源/资产要求
- 徽标、图标、吉祥物、截图和其他身份资产的品牌真实性约束
- 配置文件特定的 QA 门槛
- 已知缺失的输入

## 阶段 0：源和参考读取

对于每个源或参考演示文稿：

- 将其渲染为 PNG 或 PDF 页面。
- 制作联系表。
- 提取幻灯片文本。
- 识别哪些幻灯片是内容源、哪些是视觉目标，以及哪些模式是反模式。

对于源链接：

- 浏览或以其他方式检索实际的源页面。
- 对于财务/产品叙事，在省略客户、群组、模块、预订、保留率、指导或混合指标之前，用尽官方链接材料，如收益演示文稿、补充材料、文件和 IR PDF。
- 提取精确指标和来源日期。
- 将链接保存在源笔记和安静的演示文稿页脚或附录中。
- 切勿为了使图表更美观而编造缺失的指标。

品牌真实性门槛：

- 将徽标、吉祥物、应用图标、产品 UI、字符标记、徽章、合作伙伴标记和客户标记视为身份资产。
- 除非用户明确要求非官方概念，否则不要从头绘制、追踪、近似或风格化公司徽标、吉祥物、应用图标或标志性品牌标记。
- 使用经过验证的来源资产、用户提供的资产，或完全省略身份资产。
- 当官方资产无法验证或无法干净嵌入时，依靠颜色、排版、布局、产品语言和报告指标作为品牌线索，而不是发明伪徽标或装饰性图标。
- 在 `$WORKSPACE/source-notes.txt` 中记录每个身份资产及其来源、出处以及为什么它属于演示文稿。
- 对于模板跟随和源演示文稿任务，检查源中哪些身份资产是官方的。仅保留或借用经过验证的资产；不要创建类似标记来填充视觉空白。

创建：

- `$WORKSPACE/source-notes.txt`
- `$WORKSPACE/reference-audit.txt`
- `$WORKSPACE/data.json`（使用指标/图表时）
- `$WORKSPACE/template-audit.txt`（用于模板跟随或目标编辑模式）
- `$WORKSPACE/template-frame-map.json`（用于模板跟随或目标编辑模式）
- `$WORKSPACE/deviation-log.txt`（继承源演示文稿视觉系统时）
- `$WORKSPACE/template-starter.pptx`（使用模板 PPTX 作为起点时）

对于模板跟随和目标编辑模式，`template-audit.txt` 必须包含：

- preserve（保留）：必须保留的视觉规则
- improve（改进）：可以升级的薄弱环节
- do not imitate（不模仿）：不应复制的源人工制品
- brand/assets（品牌/资产）：徽标、颜色、图像、字体和裁剪语言
- exact clone（精确克隆）：排版、间距、继承的占位符和必须保持不变的源幻灯片骨架
- insertion contract（插入契约）：新幻灯片或对象如何加入现有演示文稿

对于模板跟随源幻灯片清单、先复制后编辑的初始演示文稿创建、就地复制幻灯片编辑和模板 QA 阻塞项，遵循 `$SKILL_DIR/profiles/template-and-edit.md`。不要对 `template-following` 使用模板代码生成、生成的模板注册表、源 PPTX 视觉跟随重建或主题匹配的新布局。

## 阶段 1：叙事框架

设计之前，将故事写为幻灯片主张。这具有约束力。

每个非附录幻灯片必须有：

- kicker（小标题）：1-3 个词命名角色，例如 `EXPANSION DRIVERS`（扩张驱动因素）
- claim title（主张标题）：结论，而非主题标签
- proof object（证明对象）：一个图表、表格、时间线、图表或视觉比较
- support note（支持注释）：简洁、事实性且有来源支持

对于财务/产品叙事，只有一个单薄图表的幻灯片通常会失败。当有助于改善论点时，首选一个主导证明对象加上紧凑的上下文栏、差异表或标注堆栈。除非支持更大的过渡，否则拒绝指标变化太小而无法承载主张的证明对象。产品图必须显示产品到业务的关联：模块或工作流、采用信号、扩张/货币化逻辑或效率影响。

不好的标题：`收入和利润率趋势`

好的标题：`增长放缓，但利润率引擎持续扩张。`

不好的标题：`扩张驱动因素`

好的标题：`积压订单的复合增长快于收入。`

如果更换公司名称后仍可使用标题，请使其更具体。

创建 `$WORKSPACE/claim-spine.txt`，包含：

- 论点
- 受众
- 单行弧线
- 幻灯片列表，包含主张、证明对象、来源和省略注释

## 阶段 2：设计系统锁定

在编写幻灯片模块之前创建 `$WORKSPACE/design-system.txt`。

设计系统必须定义：

- 幻灯片尺寸，通常为 `1280x720`
- 背景系统
- 仅使用已安装字体的排版配对
- 带使用规则的调色板
- 图表语法
- 图表语法
- 连接器语法
- 容器/框语法
- 来源/页脚语法
- 页码标记语法
- 标题/kicker 语法
- 数据标签语法
- 品牌资产政策和身份资产来源
- 允许的品牌线索与禁止的徽标/图标/吉祥物近似
- 允许的布局系列
- 禁止的主题

仅对于 `create` / 从头开始的演示文稿，默认可读的排版范围：标题 `34-52px`，封面或章节主张 `56-72px`，正文 `18-26px`，图表/表格标签和说明 `12-16px`，以及来源/页脚文本仅在不属于核心阅读内容时使用 `9-11px`。定义三种颜色的工作调色板：中性/基础色、主要强调色和次要/支持色。优先选择单色加强调色或类似色加对比色调色板，而不是无关的颜色集合。

对于 `template-following` 和 `targeted-edit`，不要强加新的排版或调色板范围。记录继承的系统并保留它，除非用户要求重新设计。

对于高级分析演示文稿，优先选择：

- 温暖纸张或深色墨水背景，而非默认浅色仪表板
- 用于主张的展示衬线或精致展示字体
- 用于标签的实用无衬线字体
- 细线而非框轮廓
- 开放构图而非重复卡片
- 图表上的直接标签而非沉重图例
- 更少的对象但更强的层次结构
- Kickers 必须作为一个视觉单元对齐：标记中心和标签中心共享同一 y 轴，字母间距的全大写标签必须在足够呼吸空间的框中垂直居中，以避免基线偏低。
- 使用标准的 kicker 构造而非手动调整每张幻灯片：
  - 标记和标签必须作为一对命名，例如 `kicker-marker` 和 `kicker-label`，或 `kicker-01-marker` 和 `kicker-01-label`
  - 标记和标签框应在 `<= 1px` 内共享相同的垂直中心
  - 标签框必须使用中间垂直对齐和足够的高度，以避免渲染/导出后字形偏低
  - 如果幻灯片上出现多个 kicker 行，请一致地为配对名称添加后缀，以便 QA 可以验证每一行

不要使用单调的调色板。除非有刻意的次要对比，否则不要让青色、海军蓝、米色、紫色或灰色占主导地位。

## 阶段 3：联系表规划

在构建幻灯片之前，创建 `$WORKSPACE/contact-sheet-plan.txt`。

对于 10 张幻灯片的演示文稿，使用至少 5 个不同的宏观布局系列，例如：

- 带指标栏的封面
- 编辑产品图
- 带边距注释的水平条形证明
- 环形图或混合证明与排名证据表
- 带右侧 KPI 堆栈的折线图
- 带侧面摘要栏的连续条形图
- 带边距标注的双系列现金图表
- 路线图时间线
- 密集附录表
- 深色附录/来源页面

硬性门槛：

- 10 张幻灯片的演示文稿中不超过 2 张卡片网格幻灯片
- 不能有 3 张连续幻灯片共享相同的宏观布局
- 不能重复 `标题 + 副标题 + 盒装面板网格` 的节奏
- 除非数据关系需要包含，否则不要使用圆角卡片默认值
- 不要在散文周围使用装饰框

联系表在读取细节之前必须看起来像是精心设计的。

## 阶段 4：可编辑构建

对于模板跟随模式，不要创建模仿源演示文稿的新幻灯片。使用导入的初始 PPTX 作为可编辑的 artifact-tool 演示文稿，就地修改复制的源幻灯片，然后导出编辑后的演示文稿：

```js
const presentation = await PresentationFile.importPptx(await FileBlob.load(starterPptx));
```

### 结构化视觉精度契约

图表、图表、连接器、框、表格和流程是高风险证明对象。将它们视为几何系统，而非装饰。

不要引入新的装饰性自定义 SVG、斑点、徽章、装饰品或不编码数据、层次结构或经过验证的品牌身份的类似图标的形状堆栈。在 `template-following` 或 `targeted-edit` 中，不要仅仅因为装饰性而剥离继承的源演示文稿装饰。

在创作任何结构化视觉之前，定义：

- 视觉必须证明什么
- 主要阅读顺序
- 每个节点/标记/系列及其含义
- 每条边/连接器及其编码的关系
- 每个容器/框及其表示的分组或包含关系
- 预期的对齐、间距和标签附着规则

硬性构建规则：

- 连接的系列必须渲染为一个连续的可编辑路径或经过验证的原生图表系列。不要用单独旋转的矩形、断开的笔触、浮动斜杠或装饰性箭头伪造线条。
- 每个连接的系列必须穿过其预期的标记，并在渲染/导出后保持正确的点顺序。
- 在图表中，连接器必须可见地附着到正确的源和目标，遵循预期方向，避开无关对象，并干净地终止而没有模糊的交叉。在 JSX 中，使用连接器附着属性，如 `fromElement`、`toElement`、`fromSide` 和 `toSide`；在形状 API 中，使用 `slide.shapes.connect(from, to, ...)` 而非断开的线段。
- 除非方向性很重要，否则不要使用箭头。如果方向很重要，箭头头必须一致、清晰且在语义上有意义。
- 框必须暗示真实的分组、比较、通道、阶段或包含关系。移除仅装饰散文的容器。
- 同等角色的框必须共享精确的高度、对齐、填充、边框逻辑和文本处理，除非层次结构有意不同。
- 框内的文本必须有足够的填充，切勿紧贴边缘、与线条碰撞或依赖收缩适配作为默认值。
- 盒装散文/标注使用最小 `12px` 垂直内部填充，当框包含 2 行以上或深色背景文本时使用 `16px`。如果框只有接近零的底部空间才看起来正确，请放大框或缩短文本。将此映射到创作表面：JSX 布局框可以使用 `padding`；导入或形状文本应使用 `shape.text.insets`；段落间距应使用 `spaceBefore` / `spaceAfter`，而非手动间隔形状。
- 任何从填充标注/指标容器开始并溢出该容器边缘的文本都是硬性失败，即使溢出的行不再被布局脚本归类为框内子元素。
- 标签必须锚定到它们描述的标记、系列、框或连接器。查看者不应需要猜测哪个标签属于哪个对象。
- 重复的指标栏/KPI 堆栈必须在每个项目上保留其完整语法：如果模式是 `值 + 标签 + 上下文`，每个项目必须在其背景上清晰地渲染所有三个部分，并具有足够的对比度。
- 预览可见的缺陷优先于布局脚本的静默：孤立标签、重复指标模式中缺失的值、标记位于副本顶部，或任何在全尺寸下看起来明显偶然的对象，即使导出和布局检查成功，也必须视为构建失败。
- 表格和矩阵必须在缩略图审阅下保留行/列语法：标题、基线、对齐和强调必须在视觉上保持一致。
- 如果图表或图表需要太多例外才能保持清晰，请用更简单的视觉重新构建，而非修补几何缺陷。

artifact-tool presentation JSX 图表注意事项：

- 当 API 可以表示图表时，尝试使用原生 `slide.charts.add(...)`。
- 除非新验证，否则不要设置 `chart.yAxis.majorGridlines` 的样式；它可能会在导出时失败并显示 `this[#h].toProto is not a function`。
- 不要通过添加零值辅助系列来伪造逐点条形颜色。如果原生图表无法清晰表达视觉效果，请使用可编辑形状和直接标签重新构建图表。
- 对于线条、趋势或连接系列视觉，当 API 可以清晰表达图表时，优先使用经过验证的原生折线图。如果使用基元创作，请将系列绘制为穿过数据点的一个连续可编辑自定义路径/折线。
- 不要从单独旋转的矩形或短段形状构建线条系列；这些可能会导出为分离的斜杠或断裂的伪箭头。
- 在 `$WORKSPACE/qa/comeback-scorecard.txt` 中记录选择。

鼓励对图表、图表和抽象产品流程使用可编辑基元。但这不是制造品牌标记的许可。不要创建类似品牌的图标、吉祥物、应用标记、合作伙伴标记或伪徽标作为装饰或填充空白。如果资产未经过验证，请用更强的层次结构、数据、文案或抽象形状来解决幻灯片问题。

## 阶段 5：改进评分标准

如果任务模式是 `template-following`，跳过改进评分标准，遵循 `$SKILL_DIR/profiles/template-and-edit.md` 进行 QA。本节其余部分仅适用于非模板模式。

在 `$WORKSPACE/qa/comeback-scorecard.txt` 中对渲染的联系表和全尺寸幻灯片评分。

每个维度为 0-5 分：

- `story`（故事）：标题是主张；序列有真实的弧线
- `specificity`（特异性）：演示文稿在名词交换测试中会失败
- `rhythm`（节奏）：联系表有多样的宏观布局
- `whitespace`（留白）：幻灯片呼吸而不显得空洞
- `chart clarity`（图表清晰度）：图表证明一个句子，标签直接，几何形状连续/正确附着
- `typography`（排版）：字体感觉有意图，而非默认
- `restraint`（克制）：没有填充框、徽章或装饰性杂物
- `precision`（精度）：指标和来源注释准确
- `coherence`（连贯性）：整个演示文稿有一个视觉系统
- `reference delta`（参考增量）：明显优于目标参考（如果提供）

交付前的最低要求：

- 提供参考时总分 >= 44/50；否则 >= 40/45
- 无维度低于 4 分
- 提供参考时 `reference delta` >= 4；否则标记为 `n/a` 且不声称超越参考

配置文件门槛是通过/失败的，高于数字评分标准。即使视觉分数很高，如果配置文件门槛失败，演示文稿也会失败。常见的配置文件阻塞项：

- `finance-ir`：虚构或无支持的指标、混合单位、缺失脚注，或看起来很好但与来源不一致的图表。
- `product-platform`：通用功能卡片、无意义的架构框、没有采用或货币化证明的模块列表，或缺失采用/业务关联。
- `gtm-growth`：没有进展逻辑的漏斗标签、弱品牌契合度、捏造的品牌标记，或无证明支持的货币化主张。
- `engineering-platform`：技术上模糊的图表、剥离真实含义的标签，或压倒高管故事的开发人员细节。
- `strategy-leadership`：没有论点进展的章节分隔符，或在运营计划中从未返回的市场框架。
- `consumer-retail`：看起来像库存的图像、裁剪质量差、未验证的资产来源，或感觉通用的客户外展文案。
- `targeted-edit-data`：计算错误、错误排名，或看起来像粘贴的新幻灯片。
- `targeted-edit-media`：未验证的身份、不一致的头像裁剪，或本地布局损坏。
- `appendix-heavy`：不可读的表格、缺失索引，或隐藏答案的来源密度。
- `brand authenticity`（品牌真实性）：捏造的徽标、吉祥物、应用图标、标志性标记、未验证的产品 UI，或用作装饰的伪官方标记。

如果提供了参考演示文稿，编写直白的逐幻灯片比较：

- 此演示文稿超越参考的地方
- 参考仍然胜出的地方
- 迭代后改变了什么

## 阶段 6：机械验证

最终交付前：

- 确认最终 PPTX 存在且非空。
- 确认包中的预期幻灯片数量。
- 确认没有空媒体文件。
- 确认需要原生图表时的图表包部分，或记录为什么使用创作的可编辑图表基元代替。
- 通过 artifact-tool 将每张最终幻灯片渲染为 PNG。
- 检查 artifact-tool 联系表的缩略图大小和全尺寸 PNG 渲染是否有视觉错误。
- 在全尺寸渲染审阅期间，显式验证重复的 UI 语法，如 KPI 栏、步骤序列、图例和预测条，确保完整性和对比度：无空白值槽、无背景上同色文本、无与阅读路径冲突的装饰标记。
- 对于每个图表、图表、矩阵、连接器系统和框系统，在全尺寸下检查渲染的幻灯片并验证预期的几何形状：
  - 连接线连续且穿过正确的标记
  - 条形/点/标签对齐到相同的基线或轴逻辑
  - 箭头和连接器附着到预期对象且不浮动
  - 箭头指向预期的阅读方向
- 共享角色的框对齐、携带等效填充，且不裁剪或挤压文本
- kickers/眉行光学对齐：图标、线条和标签位于一条中心线上，而非低或漂移的文本基线
- 使用 kicker 命名约定，以便布局 QA 可以验证中心线对齐；未命名的 kicker 行是 QA 缺口，而非通过。
- 盒装散文和标注保持可见的顶部/底部呼吸空间，特别是在深色填充和多行语句上
  - 分组对象在缩略图大小下作为连贯系统读取
- 检查联系表和全尺寸渲染是否有非官方徽标、应用图标、吉祥物、产品 UI、合作伙伴标记和客户标记。确认每个身份资产在源笔记中经过验证或移除它。
- 不需要、捆绑或假设 LibreOffice 或任何其他外部渲染器。如果兼容的渲染器已可用且用户要求，可以将其用作非阻塞性额外 QA。
- 运行布局检查并修复所有错误。只有当它们是有意的表格/轴/标签构造的已知误报且渲染的幻灯片干净时，才可以保留警告。
- 不足的框填充和填充标注中的文本溢出是错误，而非可接受的警告。

## 阻塞性反模式

交付前修复这些问题：

- 标题陈述主题而非结论
- 幻灯片使用多个主导证据对象
- 图表在直接标签效果更好时有图例
- 图表显示数据但不能证明标题
- 连接系列图表渲染为分离的笔触、浮动斜杠、伪箭头或错过标记的路径
- 线条或连接器几何形状在渲染/导出后改变含义
- 连接器浮动、附着到错误对象、穿过无关结构或指向模糊方向
- 箭头是装饰性的而非语义性的
- 框系统暗示内容不支持的分组
- 同等角色的框明显不对齐、填充不一致或样式不同
- 标签在视觉上与其描述的标记、系列、连接器或框分离
- 重复的 KPI/指标栏在任何项目上省略必需的值、标签或上下文行
- 标记、节点、字形或强调形状明显位于可读副本之上
- 值在技术上存在但因与背景对比度不足而在视觉上丢失
- 表格或矩阵在缩略图大小下失去其行/列语法
- 证明对象太薄而无法承载主张
- 产品或架构图缺少采用、货币化、扩张或效率关联
- 可见容器比内容更突出
- 圆角卡片用作默认支架
- 连续三张幻灯片共享相同的构图
- 联系表读起来像模板包
- 联系表有干净的幻灯片但信息架构薄弱
- 正文仅用于填充空间
- 附录干净但不可读
- artifact-tool 渲染有明显的换行标签、碰撞、尴尬的垂直文本或拥挤的标注
- 页脚/来源/页码标记改变样式
- kicker 图标和标签在同一行上没有光学居中
- kicker 行是手工构建的，没有命名的标记/标签对，阻止 QA 验证其对齐
- 盒装散文固定在底部边缘或缺少可见的垂直呼吸空间
- 排版回退到默认值而没有意图
- 低分辨率徽标或粗糙的图像裁剪
- 捏造或近似的官方徽标、吉祥物、应用图标、产品 UI 或标志性品牌标记
- 仅用于填充空白的类似品牌图标
- 无来源的合作伙伴/客户徽标、产品截图或品牌徽章
- 无支持的指标或模糊的来源标签
- 输出仅匹配参考而非超越它
